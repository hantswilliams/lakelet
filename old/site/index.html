# why

Most teams pay by the second for a computer they already own.

A cloud warehouse makes sense at a petabyte. Below a terabyte, a laptop with DuckDB is usually faster, and it doesn't tick.

Lakelet keeps your tables as Apache Iceberg in your own bucket, runs dbt Core against them on your machine, and checks each run before it starts. If it fits, it runs for free. If it doesn't, one click sends that one run to a worker that lives for a few minutes and shuts itself off.

Nothing is locked in. Point Snowflake or Spark at the same bucket tomorrow and everything is still there.

# one box

One box. Ask in English or write SQL. Either way, you see the SQL.

Type a question and Lakelet writes the query in front of you, editable, and runs the gauge before it runs anything. Type SQL and it just runs. The engineer ignores the English; the founder ignores the SQL. Nobody is asked which one they are.

Your dbt project as-is. DAG coloured by verdict. lakelet run --burst auto in CI with a per-project cap. Your tables readable from Spark, Trino or Snowflake through an open Iceberg catalog.

# for agents

Agents are about to run a lot of SQL. Give them a lakehouse with a budget.

More than 60% of new Supabase databases are now launched by an AI tool rather than a person. Analytics is next: agents that load data, write models and answer questions on their own. Lakelet is built to be used that way from the first release, and it ships with the guardrail the incumbents lack: an agent has to ask the gauge before it runs, and it cannot spend past the cap you wrote.

~/.config/claude/mcp.json · lakelet mcp
// one line to give an agent your tables, the gauge, and a budget
{
  "mcpServers": {
    "lakelet": {
      "command": "lakelet", "args": ["mcp", "--project", "~/acme-analytics"],
      "env": { "LAKELET_AGENT_CAP_USD": "2.00" }
    }
  }
}

// read tools on by default; write tools opt-in per project in lakelet.toml

The gauge as a guardrail estimate

An agent asks before it runs. Green runs; Red comes back as a cost and a time the agent can reason about, not a surprise bill. The same verdict humans see, as a tool result.

A cap per agent, per day LAKELET_AGENT_CAP_USD

Set once. The worker enforces it; past it, calls are refused with the remaining budget. An autonomous loop cannot spend more than the number you wrote.

Everything it did, in git save_question

Questions an agent saves become dbt models with tests and a commit that names the agent. Review the diff like any other PR.

Legible to models AGENTS.md llms.txt

lakelet init writes an AGENTS.md describing your tables, the gauge and the cap, so any coding agent that opens the folder knows how to behave. The docs ship as llms.txt. Full agent reference →

# for engineers

For engineers: what changed in 2026, and what Lakelet does with it.

You bring the laptop and the bucket. Lakelet brings the catalog, the estimate, and the worker. Everything underneath is open and versioned.

DuckDB 1.5.3 writes IcebergMERGE INTO, ALTER TABLE, bucket() and truncate() partition transforms, Iceberg V3 deletion vectors and row lineage, from an embedded engine against any REST catalog. Released May 29, 2026.
No Spark cluster to write a tableUntil May, writing Iceberg meant running Spark. A JVM cluster to append rows to a table on your own laptop is the thing this release removed. Lakelet never starts one.
An open catalog, not a Lakelet oneLakelet ships its own Iceberg REST catalog: SQLite in the binary, Postgres when hosted. It is Polaris-compatible and you can attach Polaris, Lakekeeper or S3 Tables instead. Spark, Trino, Snowflake and Athena read what Lakelet writes.
The engine stays MITAWS acquired DuckLabs on Aug 26, 2026. The DuckDB project was explicitly not acquired and remains under the independent DuckDB Foundation. Lakelet owns the catalog, the gauge and the burst path, not the engine.

Security in one paragraph: hosted Lakelet stores catalog metadata, job specs and metrics, never data files. Workers get a single-use job token and storage credentials scoped to the table prefixes in that job, expiring with it. No inbound network on a worker; outbound only to your bucket, the catalog and the control plane. SQL text is kept for the duration of the job unless you opt into history.
