# setup · one line per client

Connect an agent.

Lakelet ships a stdio MCP server. Point your client at lakelet mcp with a project folder and a daily cap. Read tools work immediately; write tools stay off until you enable them in lakelet.toml.

~/.claude/mcp.json · or: claude mcp add lakelet -- lakelet mcp --project .
{
  "mcpServers": {

      "args": ["mcp", "--project", "."],
      "env": { "LAKELET_AGENT_CAP_USD": "2.00" }
    }
  }
}

# tools

What the agent can call.

Read tools are always on. Write tools are opt-in per project. burst requires a cap on every call and is refused without one.

list_tables()Tables in the catalog with size, row count and location (local or bucket)listread

# permissions & budget

Two settings. The agent cannot change either.

lakelet.toml
[agents]
allow         = ["save_question", "burst"]   # write tools this project permits
daily_cap_usd = 2.00                            # per agent, per day; env var overrides down, never up
history       = false                           # keep SQL text an agent ran? default no

# read tools are always on
# no tool can edit this file or AGENTS.md

What a refusal looks like

Past the cap, a call returns a structured refusal, not an error: {"refused": true, "reason": "daily cap", "remaining_usd": 0.00, "resets": "2026-09-08T00:00Z"}. Agents handle it the way they handle any tool result; loops end cleanly. A healthy number of refusals in the log is proof the cap works.

On the Team tier each agent gets its own identity and budget, set in the team settings and enforced by the control plane rather than the laptop.

# AGENTS.md

The contract in the folder.

lakelet init writes an AGENTS.md next to the project. Any coding agent that opens the folder reads it before touching anything. Regenerated when tables change; never editable through a tool.

~/acme-analytics/AGENTS.md · generated by lakelet init
# acme-analytics · Lakelet project

This folder is a Lakelet lakehouse: DuckDB + Apache Iceberg + dbt. Data lives in
./warehouse (local) and s3://acme-data/warehouse (published). Catalog: ./.lakelet/catalog.db.

## Tables
orders (412 MB, local) · customers (2.1 MB, local) · events (48 GB, s3://acme-data)

## Rules
- Call estimate before query on anything touching events. Red means do not run locally.
- burst needs a cap. Default cap for this project: $0.50 per run. Daily budget: $2.00.
- Save reusable questions with save_question; they become dbt models with checks.
- Do not modify lakelet.toml, AGENTS.md, or anything under .lakelet/.
- Prefer SQL that reads from dbt models (stg_*, fct_*) over raw tables.

## Conventions
dbt project at ./ (dbt-duckdb). Models in models/. Run with lakelet run. Tests are "checks".

# for platforms · Team tier, 2027

Provision a lakehouse for your user. Never host their data.

If you build an AI app builder, a notebook, or a BI tool, your users' apps already have data and no warehouse. A management API and a remote MCP let you create a Lakelet project for a user in their bucket, set their cap, and hand back credentials, the way AI builders provision Supabase projects today.

POST https://api.lakelet.dev/v1/projects
{
  "name": "acme-analytics",
  "owner": "user_8f3a",                        // your user; they own it
  "bucket": "s3://acme-data/warehouse",        // their storage, not yours
  "source": { "postgres": "env:APP_DB_URL" },   // optional: nightly Iceberg snapshot
  "agents": { "daily_cap_usd": 2.00 }
}

// response
{ "project_id": "prj_…", "mcp": "https://mcp.lakelet.dev/prj_…", "install": "brew install lakelet" }

What your user gets

A lakehouse on their laptop that already knows their app's tables, an ask box, the gauge, and a cap. Their data stays in their bucket. They can leave you and keep it.

What you get

An analytics layer for the apps you generate without hosting a warehouse, a white-label option, and per-user budgets you control. Talk to us if you want to be an early platform partner.

# security posture

Stated once.

Defaults

Read-only by default. Writes and bursts opt-in per project and always capped. SQL text an agent ran is not kept unless history is on. Sample rows are truncated and never executed. No tool can edit lakelet.toml, AGENTS.md, or anything under .lakelet/.

Credentials

Agents get the same short-lived, prefix-scoped storage credentials people get, vended per call by the catalog. Workers have no inbound network. Prompt injection through table contents is treated as a first-class threat: model context is data, never instructions.

# faq

Questions people ask first.

Does the agent need my model key?

No. The MCP server exposes tools; your agent brings its own model. The ask box inside the app is separate and uses whichever provider you configured, or a local one.

Can an agent run up my cloud bill?

Not past the cap. burst needs a cap per call and the daily budget ends the day. The worker enforces it; the control plane refuses beyond it. The log shows every refusal.

Does this work with no internet?

Yes, for everything local. Read tools, query, import_file and save_question run on the laptop. Only burst and publish need a network.

What does Lakelet see?

Nothing, in the free tier with no bucket connected. With calibration sharing on: estimate, actual, operator counts, machine class. Never SQL, table names, column names or values.
