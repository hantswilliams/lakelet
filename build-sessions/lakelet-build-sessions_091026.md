# Lakelet — build session log, September 10, 2026

*Planning session for the desktop shell · Hants and Claude (Fable 5.1) · Produced `app-v0-plan.md` (app v0, revision 1); no code*

## 1. What this session did

- Hants set the constraints for the shell: fast, easy to ship on macOS and Linux (Windows if free), and not Electron. Re-examined the docs' standing decision (Tauri 2, React, Python sidecar, HTTP plus Arrow on loopback) against Electron, Wails, Flutter, Qt via PySide, and the Rust-native GUIs; Tauri 2 holds, for the reasons in A1. The honest cost is recorded: the installer's size and the launch time are the sidecar's, not the shell's.
- Wrote `app-v0-plan.md` in the shape of `core-v0.5-plan.md`: the A block (A1 to A14) with recommendations and tick boxes; scope for session 6 (screens 1 and 2 of the mockups); the architecture (one sidecar per window, `serve.json` for port and token, the webview calling `/api` directly, the query path from headers to batches); a build order of six steps each ending in a test; the toolchain; the definition of done; five known unknowns; the doc changes it implies. Three small core additions are named for step 0: `serve --memory-limit`, a `serving` readiness line on stdout, and a dev-only `LAKELET_DEV_ORIGIN` for testing the frontend in a browser.
- Recommendations that amend the docs: CodeMirror 6 instead of Monaco for the SQL editor (launch budget); the auto-chart in session 6 rather than 7; crash recovery in session 6 (it is F0.8's acceptance criterion).

## 5. Step 3, built

Screen 2. Assumptions stated at the start: CodeMirror's SQL package has no DuckDB dialect (A3 said it did; it has PostgreSQL, the nearest, used here with the project's tables and columns fed in for completion); TanStack Table is left out until the grid needs sorting or resizing, since with a fixed column list from the schema it would add a dependency for nothing (A4 names it; a deviation, recorded here, not a decision changed); the grid stops reading at 100,000 rows by cancelling the stream, which the core records as stopped early, and the footer says so; screen 2's code is loaded lazily because Arrow and CodeMirror are 580 kB and the launch budget is the first paint's.

Two core changes, both found by the gate rather than planned. The `X-Lakelet-*` headers were sent but not named in `Access-Control-Expose-Headers`, so a window on another origin could not read them: fixed with `VERDICT_HEADERS`, asserted in step 9's CORS test. The Esc test then showed that a client going away did nothing to the statement: a 20 M-row sort kept running for nobody, holding the engine lock so the next request (even `/health`) waited a minute. Now `Engine.interrupt()` wraps DuckDB's `interrupt`; the query route watches for the disconnect while the estimate and first execution run on a thread; the stream is an async generator that abandons its thread on cancellation, interrupts, and closes the sync generator from a helper thread once DuckDB has let go, which closes the result and frees the lock; `Result` treats `InterruptException` as a stop, not an error (`Interrupted` before the first batch, a quiet end mid-stream), so history has the run with what was measured and no error. `anyio` became a declared dependency since the API imports it. A core test covers both moments (before the first row, mid-stream) and asserts `/health` answers within ten seconds and the next query runs.

What exists now. `lib/arrow.ts` (`runQuery`: the fetch with the abort signal, `RedRefused` from a 409 with the estimate, the verdict from the headers, `RecordBatchReader.from(body)`, rows as plain values with BigInt and Arrow wrappers flattened, the cap by returning false); `SqlEditor` (lineNumbers, history, completion, Mod-Enter, Escape, the theme in the site's tokens); `GaugeLine` with its `RunState` (idle, estimating, running with the count, done with rows and seconds and the cap's footer, stopped, refused with the button, error); `Grid` (TanStack Virtual over absolute-positioned rows, numeric columns right-aligned, ∅ for null); `screens/Query.tsx` (the abort controller, batches flushed once per animation frame, the first batch flushed at once and its time stamped, `lakelet sql` beside Run, "Stop (Esc)" while running). `App` shows it once the project has a table, above the tables panel and the drop zone.

Gates, all green in the container: Playwright 13 (the four new ones: the 20 M-row table with the verdict at 1.26 s, the first 38,000 rows in the grid at 1.50 s and 66,667 rows done at 2.15 s, stamped by the page itself since a test's polling is too coarse to see a 0.9 s stream; Red with "Needs more machine" and "cap $" until "Run anyway", history reading `refused` then `local`; Esc on a sort of 20 M rows to "stopped" with the run in history and the next query running, 2.4 s in all; a binder error as a line); Vitest 14; `cargo test` 7; core suite in full. Playwright's setup now starts four sidecars and imports the 20 M-row Parquet (7 s).

Hants ran the gates on the Mac and all four step 3 tests failed, three ways, none of them the app: Playwright's `Control+A` and `Control+Enter` are not CodeMirror's Mod on macOS (⌘), and typing SQL key by key met the editor's own bindings, leaving a stray `/* */` in the box; and the sort of 20 M rows the Esc test relied on being slow takes 0.18 s on the Mac, so the query was done before Esc was pressed. The tests now pick the modifier by platform, insert the SQL as text rather than keystrokes, and stop a 10^10-row cross join, which is slow on any machine. Two things in the app changed with it, both improvements: Escape closes an open completion before it means cancel (the completion keymap comes first), and Esc cancels from anywhere in the window, not only inside the box (F0.8.6), through a window listener.

With those, the Mac ran all 13 green in 12 s on four workers, and answered the container's numbers: the verdict at 56 ms, the first 7,000 rows in the grid at 62 ms, all 66,667 rows at 143 ms, over a 20 M-row scan; the 20 M-row Parquet imported in 1.0 s; spawn to ready 436 ms warm. The 1.26 s verdict in the container was the container. One thing still worth understanding: the first Arrow batch reaching the page carries several thousand rows (7,000 on the Mac, 38,000 in the container), meaning the server had that many batches written before the browser read the first; if the first rows are to arrive as early as the core produces them, the response's first flush is the place to look (step 4 or later).
