## 3. The probe, built

`gauge/inputs.py`: the probe no longer involves DuckDB. `_write_uncached` writes 512 MiB of random bytes (a 4 MiB `urandom` block, repeated, so no controller compresses it) and `_read_uncached` reads them back, both through `os.open` with `O_DIRECT` on Linux (an anonymous `mmap` as the page-aligned buffer, `os.writev` and `os.readv` in 4 MiB chunks) or `fcntl(F_NOCACHE)` on macOS, the read returning seconds and the method. The write has to bypass the cache as well: Hants' first run of `lakelet gauge probe` on the Mac reported 16,592 MB/s with `F_NOCACHE` on the read alone, because macOS serves pages that are already in memory (the write had just put them there) even to a no-cache read; Linux's `O_DIRECT` reads from the disk regardless, which is why the container was honest from the start. A figure above 20,000 MB/s is treated as a bypass that did not bypass and falls to the cached path; when neither works the file is read through the cache twice, the second time kept, capped at the ceiling, method `cached`. `probe_throughput` returns a `ProbeResult(mbps, method, size_bytes)`; `probe_method(cache)` reads the method back from `machine.json` and calls a figure with none recorded `cached`, which is what every project from before today has. `Project.run_probe` is the one place that runs it and writes the cache, used by `init` and by the new `lakelet gauge probe [--mb]`. `init` says "up to N MB/s (measured through the cache…)" when it had to; `gauge history` opens with the disk line and, for a cached figure, the instruction to re-probe; `/api/health` gains `throughput_probe`; the app's tile reads "local disk (cached; run lakelet gauge probe)" with the reason in its tooltip.

Measured in the container with `O_DIRECT` on both sides: 5,090 MB/s for 512 MiB in 1.0 s (the container's disk is a virtual one with a host behind it, so the figure is what the guest can get, not a bare NVMe). The Mac's number is Hants' to see after the write-side fix: the first attempt said 16,592.

## 4. Expiry, built

`config`: `catalog.keep_snapshots_days` (7) in the section, the default file, and `SETTABLE`, so `lakelet config set` and the app's settings panel take it. `tables.py`: `_expirable(md, keep_days)` (older than the retention, not the current snapshot, not a branch or tag target), `_referenced_files(md, only, exclude)` (manifest lists, manifests, data and delete files with their sizes, across the chosen snapshots), `_orphans(location, kept, grace)` (data and manifest files under a local table's own `data/` and `metadata/` that no snapshot references and that are older than the grace period, an hour by default; metadata JSON stays), and `expire(name, keep_days, orphan_grace_seconds)`: refuses an attached table (the `lakelet.source-prefix` property) or one outside the warehouse, loads the table through the project's own REST catalog with pyiceberg, `maintenance.expire_snapshots().older_than(newest expirable + 1 ms).commit()`, re-reads the metadata, deletes what the expired snapshots referenced and the kept ones do not plus the orphans, and reports. The catalog accepted pyiceberg's `remove-snapshots` update without a change: the commit path already applies updates with `update_table_metadata`, which is why it was built that way. `describe` gains `expirable_snapshots`, `reclaimable_bytes` and `keep_days`, and the CLI prints "N snapshot(s) older than D days, X reclaimable: lakelet tables expire <name>". `lakelet tables expire <name> | --all [--keep-days N]`; `POST /api/tables/{name}/expire {keep_days?}` with 409 `not_expirable`.

One thing found on the way: `import --replace` drops and recreates the table, and the previous table's files stay in the same folder, unreferenced by any snapshot of the new one. That is what the orphan sweep is for, and its test covers it: after a replace the old files linger, an expire inside the grace period leaves them, an expire with no grace removes exactly them and the table reads back whole.

Tests, `tests/test_expire.py`, five: a create and three in-place rebuilds (the dbt path, delete then insert) expire down to one snapshot with files removed and every remaining file present, the table reading back through DuckDB and pyiceberg, a further rebuild and expiry; the retention keeping minutes-old snapshots; the replace orphans; an attached table refused with its files untouched; the verb, the setting and `describe`'s line through the CLI. ## 17. Step 5: dbt in the core, and views in the catalog

**Views (R6), with one deviation from the brief's letter.** R6 said the dbt plugin's `view` materialisation would write the view through the catalog. It cannot: a dbt macro runs SQL and nothing else, DuckDB's Iceberg catalog refuses `CREATE VIEW` (`Not implemented Error: Create View`, checked), and the other way for a plugin to reach the catalog, a Python UDF registered on the connection, needs numpy, which the core does not carry. So the write is `lakelet run`'s: a `view` model lives in the dbt session's `memory` database while dbt runs (`macros/lakelet_views.sql`, written by `init` and by `lakelet run` into an older project if absent: a `generate_database_name` that sends view models to `memory` so every `ref()` follows, and a one-statement `view` materialisation), and after the run `lakelet run` records each one that built as an Iceberg view in Lakelet's catalog. The outcome R6 asked for holds: the view survives the process, a second `lakelet serve` sees it, the API lists it, Spark can read it. What does not hold is that a bare `dbt run` records views; a bare `dbt run` *reads* them, because the plugin loads the catalog's views into every dbt connection through the REST routes (`urllib`, no numpy).

The catalog: `store.views` (namespace, name, metadata location; `create_all` adds the table to an existing project's catalog on open), `catalog/viewmeta.py` writing and reading the view spec's JSON (format version 1, `view-uuid`, `schemas`, `versions` with one `sql` representation in dialect `duckdb`, `current-version-id`, `version-log`, `properties`; a replace adds a version and, when the columns changed, a schema; the file `<location>/metadata/<version>-<uuid>.view.metadata.json`), and the REST view routes on `server.py` (list, load, create, commit with `add-schema` / `add-view-version` / `set-current-view-version` / the property updates, head, delete), tried in the test the way a Spark client would use them. `lakelet/views.py`: `Views.put(name, sql, properties)` binds the SQL against the engine first (`SELECT * FROM (sql) LIMIT 0`, a `BadView` otherwise, and a name that is a table is refused), takes the result's schema through pyiceberg with fresh field ids (pyiceberg's converter leaves `-1`, which the first REST read showed), skips a put whose SQL is unchanged, and re-syncs the engine; `get`, `list`, `drop`. The engine: `SET search_path = 'lakelet.main,memory.main'` instead of `USE lakelet.main`, `put_view` / `drop_view` / `views` for its `memory.main` views, and `Project.open` syncs the catalog's views into it (two passes, so a view over a view binds). The gauge sees through a view to the tables it reads (`_through_views` in `query.py`, recursive; a scan the plan has and the catalog does not know gets a default width instead of a `KeyError`, which `select * from a_view` found). `tables list` and `/api/tables` list views with `kind: view` and their SQL; `describe` on a view answers with its version count; `AGENTS.md` names them; `expire --all` skips them.

**`lakelet run` (R5).** `lakelet/dbt/plugin.py` is the spike's plugin lifted (attach, the search path, the catalog's views on every connection, the search path again on every cursor; `tests/dbt_plugin.py` re-exports it); `lakelet/dbt/runner.py`: `plan` compiles through `dbtRunner` (`--project-dir` the root, `--profiles-dir`, `--target-path`, `--log-path` under `.lakelet/dbt/`, the profile rewritten on every run because the catalog's address is per process), reads the manifest, orders the models by `depends_on`, estimates each one's compiled SQL through the gauge in that order, giving the engine a `memory.main` view for each as it goes (a `view` model as itself; a `table` model not built yet as a stand-in over its query, with dbt's `"lakelet"."main"."name"` rewritten to the stand-in for the estimate only, dropped after), and `run` refuses `--burst auto` (session 8's) and any Red model until `--run-anyway`, runs dbt, records every model in history with the estimate and dbt's actual time (D7: the calibration record grows from dbt runs too), records the `view` models in the catalog with `lakelet.dbt-model` as a property and the names unqualified (`"main"."by_c"`, which DuckDB and Spark both resolve), and on a full run drops a catalog view whose dbt model is gone. `lakelet run [selectors] [--burst never|auto] [--run-anyway] [--plan]` prints the DAG (`  stg_orders  view   green  ~0.0 s`), then the results, the views recorded or dropped, the count; `GET /api/run/plan?select=`, `POST /api/run {select, burst, run_anyway}` (400 `no_burst_yet`, 409 `red_refused`, 400 `dbt`). dbt-core and dbt-duckdb are the `lakelet[dbt]` extra (`pyproject`, `uv.lock`); without them `lakelet run` says `pip install 'lakelet[dbt]'`.

Hants asked what the deviation means for a dbt user, and for it to be documented plainly. The plain version: build with `lakelet run`, not `dbt run`; both build `table` models the same way, `lakelet run` also records `view` models in the catalog so they last, a bare `dbt run` builds its views for that session only. Now said in four places: a callout at the top of `/docs/dbt` with a "why `dbt run` cannot record a view" paragraph under *Views*; the questions page and the overview's status table; `AGENTS.md`'s conventions in every new project (an agent opening the folder reads it); and dbt itself: the view materialisation prints one line per view under a bare `dbt run` ("view X is built for this dbt session only; run `lakelet run` to record it in the catalog…"), and stays quiet under `lakelet run`, which sets `LAKELET_RUN=1` around dbt.
