## 1. Step 0: dulwich, `lakelet/versions.py`, and a commit for every save

`versions-plan.md`'s G1 to G10 were accepted as written. Step 0 is the part of it that needs no screen: git inside the core, `init` making the folder a repository, and `question save` committing what it wrote.

**dulwich as a runtime dependency.** `dulwich>=1.2,<1.3` in `core/pyproject.toml` and `uv.lock` (1.2.14 resolved; the lock diff is additive, nothing else moved). `NOTICE` names the choice: dulwich is offered under Apache-2.0 or GPL-2.0-or-later at the user's option and Lakelet takes it under Apache-2.0. Its only dependency is `urllib3`, which the package already carried through pyiceberg.

**`lakelet/versions.py`.** One module owns the repository. `open_repository(root)` is `Repo.discover`, so a project inside a monorepo finds the monorepo's; a `.git` that cannot be opened at all is None here rather than an exception. `init_repository(root)` is `Repo.init` with `default_branch=refs/heads/main`. `author(repo)` reads `user.name` and `user.email` off dulwich's config stack — the same files git reads, and the same environment variables (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`), which is what the tests use to pin an identity without touching `HOME`. `commit(root, paths, message)` is the whole surface the rest of the core uses; it returns a small `Commit(id, author, unchanged, reason)` and never raises past its own boundary (G9). `short(id)` is the seven characters the CLI shows. G5's `log_path`, `show` and `restore` are step 1's and are not here yet.

**Why the commit is built by hand.** dulwich's `WorkTree.commit` commits the index, which would sweep in whatever else the user had staged — exactly G3's *not chosen*. So `commit` stages only its own paths (which is what updates their index entries, so `git status` is clean for them afterwards), then builds the new tree from **HEAD's** tree with those paths inserted, writes the commit object, and moves `HEAD`. A file the user had staged stays staged and out of Lakelet's commit; an untracked file of theirs stays untracked. The same choice answers the brief's §7 known unknown for free: building the object ourselves signs nothing, so `commit.gpgsign = true` in a global config produces an unsigned commit rather than an error. There is a test with `gpgsign`, `tag.gpgsign` and a `signingkey` set that asserts both the commit and `gpgsig is None`.

Paths the repository ignores are dropped before staging, through dulwich's `IgnoreFilterManager`. That is what makes G9's "never data" structural rather than a matter of which list a caller passes: `warehouse/`, `.lakelet/`, `history.db` and anything else in `.gitignore` cannot be committed even if asked. `versions.commit(root, [a parquet file under warehouse/], …)` is tested to commit nothing and report nothing wrong.

**`init` (G2).** After the files are written and before the extensions are installed, `Project._init_repository` looks for a repository. None: `git init` on `main`, then a commit of what `init` created, minus anything ignored — `.gitignore`, `AGENTS.md`, `dbt_project.yml`, `lakelet.toml`, `macros/lakelet.sql`, `macros/lakelet_views.sql`, `models/.gitkeep`, and not `.lakelet/catalog.db`. One already: nothing is committed and `report.repository` is `existing`. `InitReport` gained `repository`, `commit` and `git`; the CLI prints one line for each case, and `git: <reason>` when there was one.

**`question save` (G3).** The save commits `models/questions/<slug>.sql`, `models/questions/schema.yml` and, on the first save of a project, the generic test — `save question: <title>` when the `.sql` did not exist, `update question: <title>` when it did. An unchanged save writes the same bytes, so the computed tree equals HEAD's tree and there is no commit; the CLI says "no change, so no new version". `Question` gained `commit` and `git`, which is how `POST /api/questions` carries G9's `git:` line; a question read back off disk carries neither, because they belong to the save that made them. A project made before this version — Hants', the demo — has no `.git`; `commit` opens-or-inits, so it gets its repository on its next save and not on open, which is G2's last sentence.

## 2. dbt was phoning home, and the audit could not see it

Hants' first full run on the Mac was 186 passed, 5 skipped, 3 failed. A clone of his HEAD — the code before step 0 — failed the same three, so step 0 was clean and the three were pre-existing. Chasing the first two turned up something worth more than they were.

**dbt-core sends anonymous usage statistics, and `lakelet run` is the verb that lets it.** `dbt-core` 1.12 has `DEFAULT_SEND_ANONYMOUS_USAGE_STATS = True` and ships a Snowplow tracker that posts over HTTPS. Lakelet did nothing about it. `lakelet audit network` never caught it, because its quickstart is init, import, estimate, sql, question save and question run — it never invokes dbt, so the zero was true of everything it covered and silent about the one verb that hands the work to someone else's code. That is the deck's central claim failing quietly rather than loudly, which is the worse way for a claim to fail. Hants decided it the same day and it is G11 in the brief: `_invoke` sets `DO_NOT_TRACK=1` (dbt's own switch, which sets `send_anonymous_usage_stats` to false), and the audit's quickstart gains a `lakelet run` on its own line, saying so rather than failing when dbt is not installed.

The test asserts the effect, not the environment variable: after a plan, `get_flags().SEND_ANONYMOUS_USAGE_STATS` is `False` and `dbt.tracking.active_user.do_not_track` is `True`. That distinction earned its keep — the first version of this check was written against a runner still carrying a temporary patch that popped the variable, and it "proved" `DO_NOT_TRACK` did not work at all. It does; the experiment was wrong.

**The audit's guard has a blind spot, and it is why the container cannot prove any of this.** With the telemetry deliberately left on, `lakelet audit network` in the container still reported zero. The guard patches `socket.socket.connect` but not `socket.getaddrinfo`, so a connection to a *name* dies at resolution on a machine with no DNS and is never counted; the self-check uses a bare IP (`203.0.113.1`), so it passes and gives false confidence. Measured directly: of `203.0.113.1:80`, `collector.example.invalid:443` and `snowplow.example.com:443` behind the same guard, only the IP is recorded. On a machine with DNS — Hants' Mac, and a CI runner with egress — the connect is attempted and caught, so the audit is a real measurement there and not here. Counting a non-loopback name resolution as an attempt would close it, and that is a change to what `audit network` reports, so it is a decision and not a thing to slip in. It is in "still open".

**The profile, and a correction to G4.** G11 first covered only Lakelet's own process. The profile Lakelet writes for a `dbt` run by hand (`lakelet catalog serve`, then `dbt run --profiles-dir .lakelet/dbt`) now carries `config: send_anonymous_usage_stats: false` as well, so the path `/docs/dbt` documents does not phone home either. Both mechanisms were checked against dbt 1.12 before being written: a profile-level `config:` block and a `flags:` block in `dbt_project.yml` each set the flag false, and with neither it is true. The profile was the one Hants asked for; `dbt_project.yml` is a file users edit and `_invoke` already covers Lakelet's own runs, so it was left alone. Two tests: the file carries the key, and — on the effect — dbt invoked with that profile and without the environment variable comes out with `SEND_ANONYMOUS_USAGE_STATS` false.

Separately, Hants corrected G4: the brief said "`[git] auto_commit = true` … turns the run-time commit off", which is backwards. The key defaults to **true** and setting it to **false** stops the run-time commit; saves commit either way. The sentence is fixed in the brief with the correction noted above it, the way G3's was.

## 4. Step 1: versions, restore, and a version on every run

**Reading a history (G5).** `versions.py` gained the three functions step 0 left out. `log_path(root, path, also)` walks the commits that touched the model's `.sql` or its `schema.yml`, newest first, and for each compares the blob at each path against the first parent's, so a commit the walker matched but did not actually change is dropped. Each entry carries `sql_changed`, `checks_changed` and the unified diff of the model's own file against the version before it — `difflib`, no library, which is what the app draws in step 3. `show` returns a version's content and `_resolve` accepts any unambiguous prefix of a version id, which is why the list shows seven characters. `changed(root, paths)` answers which of a set of files differ from what the repository holds; it is what the run-time commit uses to decide there is nothing to record.

A `Versions` class on the project turns a name into a path: `models/questions/<name>.sql` for a question, otherwise the first `models/**/<name>.sql`. That is resolved off disk rather than from the dbt manifest on purpose — a version list would otherwise wait for a compile, which is four to five seconds for a list that has nothing to do with compiling. The cost is that a model whose file is named differently from the model will not be found by name; no such model exists in this project, and step 4's lineage does read the manifest, so if it becomes real that is where it is fixed.

**Restore (G5).** `restore(name, id)` writes that version's bytes over the current file — the bytes, not a re-render, so what comes back is exactly what was there, dated header and all — then for a question re-derives the `schema.yml` entry from it and commits both as `restore question: <title> to <short id>`. `git log` stays linear; the restore is the third version, not a reset. A model restores as `restore model: <name> to <short id>`, which the brief does not specify and is the obvious analogue. The re-derivation needed `Questions.save`'s schema-entry logic on its own, so it is now `Questions.write_entry(slug, title, sql)`, called by both; `save` keeps its `DESCRIBE` first so a question that does not bind is still refused before anything is written.

**A version on every run (G4).** `runner.run` commits before dbt builds: the model files the manifest names that `changed` reports as different, plus `dbt_project.yml` and the macros, as `run: stg, by_customer changed`. Nothing changed, no commit. `RunReport` carries `commit` and `git`, and the CLI prints `version <short> recorded before the run`. `[git] auto_commit` is a new section in `lakelet.toml`, `true` by default, in `SETTABLE` so `lakelet config set git.auto_commit false` and the app's settings panel both reach it, and the panel's new row is worded as G4 asks: "Record a version on every save and run".

**The correction to G4.** The brief said `auto_commit = true` turns the run-time commit off, which is backwards; Hants confirmed the reading and it is now `false` that stops it, with the correction noted above the decision the way G3's was.

**The CLI and the routes.** `lakelet versions <name>` prints version, when, who, what and what changed; `lakelet restore <name> <id>` says what it restored and the new version, or that the file already held it. `GET /api/versions/{name}`, `GET /api/versions/{name}/{id}` and `POST /api/versions/{name}/restore` are the same three functions, with `no_such_model` and `no_history` as 404s carrying the sentence rather than an empty list.

**Gates.** `core/tests/test_versions_history.py`, 15 tests: two saves are two versions with the diff and the author; the first save's diff is the file arriving and the second's has the added line; "checks changed" on the first and not the second; a commit touching only `schema.yml` is listed, marked, with an empty diff; a hand-written model has versions too; a file with no commits raises the sentence and an unknown name raises `NoSuchModel`; restore writes the old SQL back as a third version and re-derives the checks; a prefix works; an unknown version says so; `show` returns each version's SQL; a run commits what it is about to build; a second run with nothing changed commits nothing; `auto_commit = false` stops the run-time commit while a save still commits; the setting is settable and defaults to true; the CLI lists and restores; the three routes. Two existing tests were updated for the new section and the new settable key.

Container: **core 201 passed, 10 skipped**, Vitest 47, Playwright 22 against seven sidecars, `tsc` clean. The CLI reference was regenerated and has the two new verbs. Docs: `/docs/questions` has the version list and restore, `/docs/dbt` has the run-time commit and the setting, `/docs/config` has the `[git]` section and its key, `/docs/api` has the three routes and the new setting.
